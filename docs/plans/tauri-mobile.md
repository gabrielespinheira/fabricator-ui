# Tauri mobile setup and demos

## Outcome

Add **Tauri** beside **React Native** in Get started’s **Mobile** selector. A user can create a Tauri mobile app on its own or combine it with a website and Tauri or Electron desktop. React Native still uses Expo and remains the default when Mobile is enabled. The existing Desktop selector keeps Electron and Tauri.

Build on [`demos/tauri`](../../demos/tauri/README.md) for the runnable iPhone and iPad demo. It already mounts the React explorer and has a small Rust-backed services page. Its [verification log](../../demos/tauri/verification.md) predates the shared explorer and records no mobile build or launch. The [mobile template](../../packages/cli/templates/mobile-tauri/README.md) is a manual overlay today. This work turns it into a supported CLI path and proves the demo and scaffold on mobile targets.

## Project layout and support

Use **React + Vite** as the shared renderer for Tauri mobile in the first release. Vite produces local assets the app can open offline, and Fabricator already has a Vite monorepo scaffold. Keep separate mobile and desktop hosts so each can use its own identifier, permissions and build settings. [Tauri’s Vite guide](https://v2.tauri.app/start/frontend/vite/) · [Platform configuration](https://v2.tauri.app/develop/configuration-files/)

| Selection                          | Generated project                                                                                                                                     |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tauri mobile only                  | `apps/web` contains the renderer. `apps/mobile/src-tauri` contains the iOS, iPadOS and Android host. The Install step shows mobile run commands.      |
| Tauri mobile + Web                 | The website and mobile host share `apps/web`. The website can be built and deployed independently.                                                    |
| Tauri mobile + desktop             | `apps/mobile` and `apps/desktop` share the same `apps/web` renderer. The desktop host can be Tauri or Electron. Web remains an independent toggle.    |
| React Native mobile                | The existing Expo app in `apps/mobile`, with its own React Native UI and dependencies. The Web and Desktop choices continue to work as they do today. |
| Desktop Tauri without Tauri mobile | The existing desktop scaffold and its supported renderer choices, including Next.js.                                                                  |

- Source installs use the selected Fabricator web base, icon library, look and App Shell. Where the existing package distribution is enabled, Tauri mobile uses `@fabricator-ui/react` from `apps/web`, with the same package-mode component catalog and restrictions as Vite desktop. Expo uses the React Native registry or package. Tauri needs no new component registry or runtime-specific copies of components.
- First-release mobile support covers iPhone, iPad and Android. Qualify iPhone and iPad first, then Android before listing it as verified. Start from the demo’s iOS/iPadOS 16.4 and Android API 24 configuration. Document the tested Android WebView baseline separately from the installable Android API level. [Tailwind compatibility](https://tailwindcss.com/docs/compatibility) · [Tauri WebView versions](https://v2.tauri.app/reference/webview-versions/)
- Each project has one mobile runtime in `apps/mobile`. A runtime change in the wizard applies to a new scaffold. Existing projects can add a Tauri host to a supported Vite workspace. Expo app migration, other mobile renderer templates, optional device plugins and store submission are separate work.

Retain input after a failed save and make retry possible. Keep the catalog usable if the native service fails.
4. Launch on iPhone and iPad simulators, then on Android. Test iPhone safe areas, iPad portrait/landscape and narrow multitasking width, Android back navigation, and keyboard opening and dismissal. Check light and dark themes, touch targets, reduced motion, focus order, iPad external-keyboard navigation, VoiceOver and TalkBack. Run the bundled frontend with the dev servers stopped. 5. Replace the dated verification baseline with evidence from the current explorer. Record device, OS, WebView version, host mode, commands and results. ## 2. Define mobile runtime in shared setup

- Add `mobileRuntime: "expo" | "tauri"` to the `packages/setup` schema with `expo` as the default. Keep `mobile` for enabled state so old URLs and setup inputs still mean Expo. Add shared queries for whether the plan needs an Expo app, a Tauri mobile host, or a web renderer. `hasWebApp` must include Tauri mobile even when `web` is false. Keep the public website toggle distinct from the renderer’s presence.
- Update the setup plan, project tree, prerequisite list, next commands and agent prompt from the resolved targets. A Tauri mobile project gets the Vite renderer and mobile host steps. Expo scaffolding, Metro configuration, Expo peer alignment, root hoisting rules specific to Expo and the native App Shell run only in the Expo path. Deduplicate Rust prerequisites when mobile and desktop both use Tauri.
- Keep `create --mobile` and `-t expo`. Add `--mobile-runtime <expo|tauri>` to enable Mobile with an explicit runtime. Using a separate flag preserves positional input such as `create --mobile my-app`. Default to Vite when the CLI receives a Tauri mobile selection without `-t`. Reject explicit incompatible templates and `--no-monorepo` with a supported command before any files are written. Generate an explicit Vite template flag from Get started. Apply the same validation in interactive flows, `--dry-run` and JSON output.

```sh
# Mobile only
npx fabricator-ui@latest create my-app -t vite --no-web --mobile-runtime tauri --yes

# Website, mobile and desktop
npx fabricator-ui@latest create my-app -t vite --mobile-runtime tauri --desktop tauri --yes

# Add a mobile host to an existing Fabricator Vite monorepo
npx fabricator-ui@latest apps add mobile tauri
```

## 3. Wire the CLI scaffold

1. Add a Tauri mobile scaffold step in `packages/cli/src/setup/steps.ts`. Reuse the template copier and Vite source/package scaffolding. Adapt `packages/cli/templates/mobile-tauri` into the `apps/mobile` wrapper. Generate workspace metadata, an app identifier with valid segments for both Apple and Android, app name and Cargo crate name. Give the desktop and mobile bundles distinct identifiers and keep the existing desktop identifier stable. Reuse the repo-pinned Tauri tooling and verify the template is present in the built CLI tarball.
2. Point the wrapper at `apps/web`. Give the Tauri mobile Vite profile its own strict dev port and build output so it can coexist with the regular web and desktop builds. Respect `TAURI_DEV_HOST` for simulator and physical-device development. Use bundled output for production and a local routing strategy that survives reload and cold start on the bundled origin. Check that browser deep links and desktop navigation still resolve. Keep renderer config changes restricted to supported file shapes.
3. Generate package-manager-aware root and workspace scripts for iOS, iPadOS and Android dev and builds. Use explicit commands such as `dev:mobile:ios`, `dev:mobile:ipad` and `dev:mobile:android` in the Install summary and README. The initial CLI scaffold should succeed without Rust or native SDKs. Provide explicit initialization commands and distinguish a missing toolchain, uninitialized target, missing simulator, port collision and build failure in launcher output. Keep signing credentials external and document signing and user-owned bundle identifiers for device/store builds. [Apple distribution](https://v2.tauri.app/distribute/app-store/) · [Google Play distribution](https://v2.tauri.app/distribute/google-play/)
4. Mount the web App Shell once in source mode. Apply mobile safe-area insets, keyboard-aware layout and responsive navigation in the mobile host. In a combined build, the desktop window adapter must activate only in the desktop host. Review detection that currently treats a Tauri bridge as a desktop signal. Check that desktop drag regions, titlebar and window-controls IPC stay out of mobile and ordinary browser contexts. Keep the scaffold’s IPC permissions and content security policy scoped to its own local app and enabled capabilities. The demo’s storage command and media permission prompts belong to the explorer’s examples. [Tauri capabilities](https://v2.tauri.app/security/capabilities/)
5. Use the same scaffold and workspace steps for `apps add mobile tauri`. Require a recognized Vite React renderer in `apps/web` and retain its installed distribution. Preflight incompatible frameworks, unsupported config shapes and a populated `apps/mobile` before writes. Return the exact manual config change for a custom Vite app. A repeated compatible command resumes missing steps. Preserve user edits, detect same-path conflicts before overwriting, and make root scripts and dependency updates idempotent. Keep bare `apps add mobile` and existing desktop forms available.
6. Extend `doctor` to recognize the host under `apps/mobile/src-tauri` and report setup readiness per target. Include the web renderer path and whether its dev/build configuration and native project are ready. Existing `init`, component installation and look updates target the renderer through the existing Vite workflow.

## 4. Add Tauri to Get started

- Reuse the Mobile row’s Fabricator Select, Switch and framework icon set in `create/_components/project-step.tsx`. Offer **React Native** and **Tauri**. Keep the runtime selection when toggling Mobile off and back on, and lock the last enabled app as today. Persist it through the existing `nuqs` setup state. Old shared links, including Expo links, keep their existing interpretation.
- When choosing Tauri with an incompatible Web framework, explain that Tauri mobile uses Vite and offer an explicit **Switch renderer to Vite** action. Commit the runtime and renderer change together. A manually edited incompatible URL shows the same recovery and disables the Install command until corrected. When Mobile is disabled or set back to React Native, restore the available framework choices and respect the currently chosen framework.
- Show the renderer relationship in the Project and Install steps. Update the file tree, component import example, generated command, prerequisites and README preview together. With Web off, explain why `apps/web` is present and surface only the chosen app start commands. Existing projects keep the current `init` experience and link to the add-host instructions.
- Base App Shell options and previews on both runtime and preview device. Tauri mobile gets a phone-sized web shell with the existing web renderer. React Native keeps its native options and previews. Desktop controls appear only in the desktop preview. A mixed setup can preview mobile and desktop separately, and shared options apply to the common shell. Test the iframe’s loading, ready and failed states so a preview failure gives a retry and leaves setup controls usable.
- Use the site’s existing responsive layout and tokens. Check keyboard selection, focus when an incompatibility appears, screen-reader names, and copy feedback. Capture before and after for the Mobile row and Install summary at phone and desktop widths in both themes. Open the running site through Relay and inspect the screenshots.
