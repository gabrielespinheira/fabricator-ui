# Data Table

A Fabricator-exclusive `data-table` item that replaces upstream's "build your own" guide with a real component: typed columns, sorting, filters in header popovers, pinned and resizable columns, 10,000 virtualized rows, pagination, infinite scroll, server mode and loading states. Web first, on every base; native is deferred with a dated exception.

References: Notion's database tables (filter operators per property type, relative date presets, cells that edit in place, the "Calculate" footer), beUI's motion table (10k virtualized rows, resize and reorder, skeleton rows, `onEndReached`), Kobra's CRM table (a type icon in each header that turns into the sort arrow, tone tags, a pinned first column, a footer of calculations), Beautiful UI's Records Table (row numbers that become checkboxes, a menu from the header, "Add calculation"). The references contribute behaviour; the look is Fabricator's.

## Decisions

- **TanStack Table v9 underneath**, as the docs already teach. `useDataTable` registers the features once and keeps state in the table's atoms, so a page passes only `data` and `columns`. Server mode is TanStack's `manual*` options plus `rowCount`.
- **Typed columns.** `createDataTableColumns<Row>()` returns builders that each produce a TanStack column with a `meta.type`: `text`, `number`, `currency`, `percent`, `date`, `status`, `tags`, `person`, `link`, `email`, `boolean`, `progress`, plus `select` and `actions`. The type picks the cell, the alignment, the header icon, the sort, the filter editor, the filter function and the footer calculation. Raw TanStack columns still work; `meta.type` opts them in.
- **One table, real semantics.** A `<table>` with `table-layout: fixed`, widths in a `<colgroup>` from CSS variables, so resizing rerenders one element. Not `role="grid"`: controls stay in tab order (APG's sortable table), headers carry `aria-sort`, rows `aria-rowindex` against `aria-rowcount`.
- **Virtual rows** with `@tanstack/react-virtual` 3.14.26, pinned (about 11.5 KB min+gzip with its core). Spacer rows above and below keep sticky headers and pinned columns working. Measured rows, so wrapped text and expanded rows still scroll right.
- **Header:** the label sorts (Shift adds a sort), the type icon turns into the direction arrow on the move timing, and a filter button opens a Popover with sort, the type's filter and the column's options (pin to start or end, hide, clear filter). The button shows when the header is lit, focused or filtered. The table's settings (density, calculations, row numbers, stripes, column lines, column visibility, clear sort, clear filters, reset columns) sit in a Popover from the header of the actions column, which the hook adds when a table has none: everything but the search happens inside the table, so there is no Filter or View toolbar.
- **Filters as Notion has them:** an operator Select and the editor it calls for, on the `surface-5` panel. Text: contains, does not contain, is, is not, starts with, ends with, is empty, is not empty. Numbers: =, ≠, >, ≥, <, ≤, between, empty. Dates: is within (today, yesterday, past week, month, year, this month, this year, next week, next month), is, before, after, on or before, on or after, between (a range Calendar), empty. Status and person: is any of, is none of (a searchable checklist with counts when rows are local). Tags: has any of, has all of, has none of. Checkbox: All, Checked, Unchecked. `matchesFilter` and `queryRows` apply them anywhere, so a server answers like the table.
- **Editing in place** with `meta.editable` and `onCellChange`: text, numbers, links and emails in an input (Enter or Tab saves, Escape cancels, typing on a focused cell replaces it, F2 edits), status and person in a picker (picking the current one clears it), tags toggle in the same picker, dates on a Calendar, checkboxes toggle. With `load`, `replaceRow` shows the change at once; with `data`, the page keeps its place (the hook owns sort, filters, search and pages, and resets the page only when those change).
- **Loader:** `useDataTable({ load })` is the recommended source. It asks for a window of rows with the view (`offset`, `limit`, `sorting`, `filters`, `search`), debounces the search, aborts stale requests, appends the next window as the scroll nears the end (infinite scroll by default) or asks for the current page with `paginate`, takes the footer's figures from the server (`summarizeRows`), and keeps rows on a failed next window with an inline retry.
- **Pinned and scrolling columns:** `position: sticky` with offsets from column sizing, opaque on `--data-table-surface` with the row's hover or selection laid over as a gradient. No rule or shadow on the pinned edge.
- **Loading:** skeleton rows on first load (footer figures wait for them), a primary sweep under the header and rows dimmed after a short delay on a refetch, skeleton rows appended while the next window loads, an error state with a retry, `DataTableEmpty` (the Empty component) for no rows and for no matches with a clear-filters action.
- **Scroll first, pages optional:** infinite scroll is the default; `paginate` plus `DataTablePagination` (rows per page Select, range text, first, previous, page numbers, next, last) is the option. `DataTableContent` still takes `loading`, `hasMore` and `onLoadMore` for hand-rolled loading.
- **Scrolling:** `overscroll-behavior: none` on the viewport, so neither axis bounces or chains to the page. Tags scroll inside their cell with `scroll-fade-x` instead of a "+N" badge.
- **Selection:** a checkbox column, optionally numbered (the number gives way to the checkbox on hover, focus or selection), Shift-click for ranges, and `DataTableSelectionBar`, floating over the bottom edge with the count, actions and clear.
- **Footer calculations:** `meta.aggregate` (`count`, `sum`, `average`, `min`, `max`, `unique`, `filled`, `empty`, `checked`, `unchecked`) over the filtered rows or from the loader, a menu in each footer cell to change it, and a switch in the settings to hide the footer.
- **Variants and view:** `variant` `card` (default: card surface, rounded) or `flat` (no frame, full bleed in a page). The view (`size` mapped to densities, `lines` rows or grid, `striped`, `footer`, `numbered`) is state people change from the settings; `defaultView`, or `view` with `onViewChange`, sets it. Rows are 48px at the default density. Sticky header always.
- **Pure model, thin UI.** `lib/data-table-model.ts` holds the filter functions and their summaries, formatters, calculations, page ranges, the load-more threshold and the selection range. Tested first.
- **Per base** only where triggers differ (Popover, Dropdown Menu, Select): `ui/data-table.tsx` in base, radix and aria. The model, the hook and the cells are shared.
- **Native deferred:** a dated `component` exception in `parity-exceptions.json`. The native example stays as it is.

## Fast scrolling (round 8)

- **Windows by position.** A loader without pages lays every match out in the scroll (`total` rows) and keeps rows by window (`indexWindows`); unloaded positions draw as skeleton rows. The windows in view load (`getWindowsToLoad`, a quarter window of lookahead either side): at once when the scroll is slower than a window a second, 120ms after it settles when faster. Requests more than a window away from the view are aborted (`getWindowsToCancel`). A failed window shows "Try again" on its first row in view. Rows from a loader take their position as id unless `getRowId` says otherwise, so selection survives windows loading around it. This replaced appending the next window near the end, which left a fast scroll waiting at the bottom of what had loaded.
- **Skimming.** Above 4px/ms, rows coming in draw as skeletons and the range extends 40 rows ahead in the scroll's direction (`rangeExtractor`); real rows return 90ms after the last fast change. Not while focus is in a row. A fling at 600px a frame went from 30 of 60 frames showing nothing to 2; at 1,500px a frame from 60 to 5 (the frames before the speed registers).
- **Spacer hairlines.** The spacer rows above and below the rows drawn carry the row hairlines, so what the compositor shows ahead of the main thread still reads as rows.

## Performance (round 6)

Measured with `tmp/data-table/bench.mjs` on a temporary 10,000-row in-memory example (dev build, docs-site CSS): scroll frames, a row checkbox, select all, a resize mousemove, a sort, a search keystroke and an edit.

- **Render boundaries.** TanStack v9's `useTable` returns a new `table` object on every render of the page that owns it and subscribes to every slice, so nothing is memoized on `table`. The footer's figures memoize on the filtered rows, the leaf columns and the format inputs (they used to rerun over every row on each click and each resize move). The header no longer depends on the selection or the column sizes: the select-all checkbox and the resize handles follow their slice with `Subscribe` (`table.store`), and select-all skips its O(rows) checks when nothing is picked. Rows depend on whether a row click handler exists, not its identity (a ref holds it).
- **Cells.** Each body cell memoizes: cells drawn from their value and editors on the row's data, the checkbox column on the selection and the row's place, other custom cells on their cell (a custom cell that shows table state subscribes to it). Picking a row redraws its checkbox, not its badges and avatars.
- **Virtualizer.** Stable `getItemKey` and `estimateSize` (a new one rebuilt every row's measurement on each render), fixed-height rows with no per-row measuring, overscan 5. `useFlushSync: false` set off a Base UI update loop, so rows still render inside the scroll event.
- **Styles.** Column widths go on the `<col>`s and pinned offsets in a scoped `<style>` rule keyed by `data-pin-column`: a custom property on the table restyled every cell on each resize move. The viewport is `contain: content`.
- **Layout reads.** The scroll layer listens before the virtualizer (a layout effect in the child), so it reads the scroll while layout is clean, reads before it writes, and caches the direction. The view-change scroll reset is skipped when the table is already at the top (it forced a layout of the new rows).
- **Search.** Each cell's search text is lowercased once and cached per column definition and row (`toSearchText`), and the query once per keystroke.
- **Person cells.** A plain image over Avatar's initials: `AvatarImage` re-renders when it loads and checks animations on mount, a forced style pass per row.
- **Hook.** `meta`, `loader` and `defaultColumn` are memoized; `editCell` is stable for the table's life and calls the latest `onCellChange`.
- **Row checkboxes.** `DataTableCheckbox` (shared cells) draws the Checkbox's markup and style-map classes on a plain `<button role="checkbox">`, for the selection column, select-all and checkbox editors. Base UI's indicator checks animations on uncheck (a forced style pass and a commit per checkbox) and Radix's `Presence` reads computed style on every mount (with `forceMount`, every checkbox): two forced passes per row scrolled in on Radix. The filter checklist keeps the real Checkbox.
- **No inherited-colour transitions.** Cells changed text colour on a transition; `color` is inherited, so every frame of it restyled every cell's contents: clearing 20 picked rows restyled 1,846 elements a frame for 6 frames. The change is instant now.

Production build (`next build`, docs-site CSS, 10,000 rows in memory; each figure includes two animation frames, about 33ms): scroll frame at 240px a frame 61ms (37ms without the site's `:has()` rules), a row checkbox 67ms (34), select all 105ms, resize move 50ms, sort 104ms, search key 112ms, edit 114ms; with `load` (the demo) sort 65ms and edit 65ms on every base. Radix scrolling went from 110 to 58ms with the light checkboxes.

Dev build, docs-site CSS, before → after: scroll frame 108 → 84ms, row checkbox 150 → 85–100ms, select all 170 → 130ms, resize move 135 → 50ms, sort 300 → 283ms, search key 150–186 → 128–150ms, edit 330 → 230ms. Most of what's left on this site is the `:has()` restyle below and React's dev-only work.

## Finding: `:has()` and inserted rows

On the docs site, every row the virtualizer inserts restyles the whole document (about 4,500–6,000 elements, ~55ms a frame in a development build), so fast scrolling drops to about 10 fps there. The cause is the site stylesheet's ancestor-position `:has()` rules (`group-has-*`, `in-[…:has(…)]`): when an inserted element could match a `:has()` argument (Avatar's `[data-size]`, the Checkbox input's `:disabled`, …), Chrome invalidates every ancestor and their subtrees. With those rules removed the same scroll restyles ~680 elements and style time over the run falls from ~970ms to ~52ms. Reordering the compound doesn't help, and chunking the rows only gathers the same work into longer freezes. The table keeps per-row, header and footer memo boundaries, and editable cells mount their popover only when opened (a popover root per cell cost about a quarter of the scroll work). The fix belongs in the style maps, replacing ancestor-position `:has()` with data attributes set by the parent. Bisecting the 535 `:has()` rules one by one (round 3, with editable rows: about 105ms a frame with them, 37ms without, in a development build) found no single culprit: Sidebar's inset wrapper (`[data-variant]`), Field label's `:focus-visible`, Search's clear button, App Nav's toggle, Multi-Select's `:active` item, App Shell's panels and Select's outline variant each restyle the whole document on their own, because their arguments key on attributes every row carries (`data-slot`, `data-variant`).
