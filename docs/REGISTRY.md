# Registry

Declaring items, building them, and which files are authored or generated. Endpoints that serve setup (`/init`, `/create`) are in [CLI.md](CLI.md).

## Declaring an item

Items are objects in each folder's `_registry.ts`, typed `Registry["items"]` from `shadcn/schema` and validated at build time.

```ts
{
  name: "stepper",                   // kebab-case; upstream's name when it replaces one
  type: "registry:ui",
  title: "Stepper",
  description: "A multi-step progress indicator with keyboard navigation.",
  dependencies: [],                  // npm deps beyond the base's index item
  registryDependencies: ["@fabricator/button"],
  files: [{ path: "ui/stepper.tsx", type: "registry:ui" }],
  categories: ["navigation"],
  meta: { fabricator: true },        // true when the item doesn't exist upstream
}
```

- **Type:** `registry:ui` (primitive), `:component` (composed), `:block`, `:page` (route), `:hook`, `:lib`, `:theme` (tokens), `:base` (init payload), `:font`, `:file` / `:item` (config or agent files).
- `registry:page` and `registry:file` need an explicit `target`; blocks use `app/<route>/page.tsx`. The CLI remaps per framework.
- **Names:** blocks `<category>-<nn>` (`login-01`); examples `<component>-example` or `<component>-<intent>`. Check exclusive names against upstream's catalog.
- New tokens ship in the item's `cssVars` (`theme`, `light`, `dark`); new CSS (`@utility`, `@keyframes`) in `css`.
- Fabricator's screen blocks are declared in `registry/fabricator/blocks.ts`: the page's route, then the block's `components/`, `lib/` and `hooks/` files, named after its subject (`sign-in-form.tsx`) so two blocks never write the same path. Pure `lib/` files get colocated tests, which are not published. Fabricator blocks compile into `styles/<base>-fabricator/blocks/`, and the Fabricator styles' index and component shards list them, so the site previews them at `/view/<base>-fabricator/<name>`.
- A Fabricator item whose registry dependencies differ by base lists the extras in `meta.baseRegistryDependencies` (`{ base: ["toast"], radix: ["sonner"], aria: ["sonner"] }` on Event Calendar); the build adds each base's to its `registryDependencies`.

## Build

- **Pipeline:** placeholders + style map → `createStyleMap` / `transformStyle` from `shadcn/utils` → `shadcn build` (`apps/web/scripts/build-registry.mts`). The build also rewrites bare `registryDependencies` to `@fabricator/<name>` and points `meta.links` at this site.
- **Full build** (canonical, formatted; before committing): `bun run registry:build`. It includes React Native, SwiftUI and Kotlin Compose.
- **Targeted** (fast, unformatted, iteration only; in `apps/web`): `bun run registry:build --examples | --indexes | --style <id|all> | --registry <id|all>`.
- **React package** runs `bun run react:build` to refresh the Base UI payloads and emit the package to `packages/react/dist`. CI uses `bun run --cwd apps/web react:build` with its existing registry output. Both commands build `@fabricator-ui/icons` before compiling the React package, which imports its declarations. The builder walks the Fabricator Icons registry closure for the supported exports, compiles package-prefixed styles, and emits ESM and TypeScript declarations. The registry and package share authored component source.
- Editing an existing example needs no rebuild; adding, removing or renaming one needs `--examples`.
- The full `registry:native` rewrites `styles/native`; avoid it while others work in the tree (`--check` writes nothing).
- `platforms:generate` resolves the shared theme, typography weights, density, motion, sounds, Data Table type defaults, component/block catalog and Fabricator icon geometry into `generated/platforms/contract.json`. Its source is the existing Fabricator modules and registries. SwiftUI and Kotlin adapters consume this contract and the licensed Inter font assets. SwiftUI reads Data Table width, minimum, alignment and first sort direction directly from these generated rules.
- `registry:platforms` runs each renderer's asset adapter and manifest generator, then exports native payloads. Edit ownership in `apps/web/scripts/swiftui/build-manifest.ts` or `apps/web/scripts/compose/generate-manifest.ts`; rebuild the committed manifests. The build verifies every public catalog entry has an owner, validates dependencies and checks that each component's native API is declared in its source closure. Payloads support binary assets and exact targets; the CLI's native adapter consumes them. Each owning module must compile independently of the example apps.
- SwiftUI's `sync-editor.ts` bundles the canonical pure editor/calendar engines and copies the existing TextKit core from `packages/editor-native/ios/` with a plain Swift event boundary. Change those owning sources and regenerate; never hand-edit the copied core or bundled JavaScript. Third-party notices ship with the bundles.
- SwiftUI supplies its variable fonts, document scaling, density-specific code metrics, native keyboard accessory and task/Copy decoration controls through that TextKit boundary. Controls use UIHostingConfiguration and stay positioned by measured, visible TextKit fragments after layout; task hit areas stop before editable text. Restyling must not position controls from estimated fragment frames. The core keeps its drawn fallback and Expo record API; no generated font-replacement patches are applied. Editor and Syntax Highlight own the shared document-size model and Geist Mono resources in their respective closures.
- SwiftUI's `sync-file-icons.ts` renders the canonical `icons-core` file SVGs through the existing `icons-static` PNG adapter. The File Tree payload owns the generated light/dark PNGs, resolver metadata and Charmed license. Change the owning artwork or generator and rebuild; foundations do not carry these optional assets.
- SwiftUI's document adapter bundles the canonical Markdown parser/tree and Syntax Highlight tokenizer into `document-engine.js`. Syntax Highlight owns that engine, notices, document typography, Geist Mono fonts/license, clipboard boundary and shared render data; Markdown depends on it. The app launcher separately generates `.build/document-examples.json` from the React Markdown, Syntax Highlight and Editor examples for the gallery and UI tests. Rebuild these resources through their generators.
- SwiftUI's launcher also extracts the canonical pure Data Table account declarations and value-column metadata through TypeScript's parser, evaluates them without React imports and validates the result with Zod. `.build/data-table-examples.json` belongs to the example app only; registry payloads never include the seeded account dataset.
- SwiftUI Calendar and Date Picker have separate source owners. Calendar depends on the shared form/Select module; Date Picker and block compositions depend on Calendar. Foundations own the pure calendar selection rules and their tests. React DayPicker attribution is preserved in the root NOTICE and synced into the native payload.
- Date Picker owns its month/year grid, pure period/page model and tests. Its text adapter bundles the canonical Date Picker parser and all installed date-fns locales into `date-picker-engine.js`, with third-party notices. Date Picker owns that engine and the shared JavaScriptCore boundary; foundations and unrelated families exclude these optional resources. Rebuild through `bundle-domain-engine.ts` and `sync-contract.ts`.

- Standalone Time Wheel owns `ui/time-wheel.swift`, its pure clock/snap/tilt model, tests and `platform/time-wheel-scroll-events.swift`. It depends only on foundations; unrelated form consumers exclude it. Its 12/24-hour values, step rounding and clamping follow the canonical time model. Explicit spacer rows and a scroll-target behavior center values on the band. Only user scroll events publish settled values; layout and programmatic centering are read-only. The adapter uses drag gestures and a scoped AppKit wheel monitor for macOS trackpads and mouse wheels. It adds no JavaScript resource.
- Time Input owns `ui/time-input.swift`, its pure parser/draft model and tests, depending on Time Wheel and Input. Date Picker depends on Time Input for canonical clock forms and the wheel. The shared iOS popup adapter can mount a nonmodal hosted surface for editable inputs while keeping its existing modal presentation for other overlays. Its portal mounts beside the SwiftUI hosting view in the common superview, preserving SwiftUI's ownership of its view hierarchy. The input's anchor remains hit-testable, and keyboard avoidance stays in the shared overlay layer.

## Output

| Output                         | Path                                                  | Served at                                  |
| ------------------------------ | ----------------------------------------------------- | ------------------------------------------ |
| Published items                | `public/r/styles/<base>-fabricator/<name>.json`       | `/r/fabricator/<base>-<style>/<name>.json` |
| The same with Fabricator Icons | `public/r/styles/icons-fabricator/<base>/<name>.json` | the same URL with `?icons=fabricator`      |
| Native items                   | `public/r/native/`                                    | `/r/fabricator/native/<name>.json`         |
| SwiftUI items                  | `public/r/swiftui/`                                   | `/r/fabricator/swiftui/<name>.json`        |
| Kotlin Compose items           | `public/r/compose/`                                   | `/r/fabricator/compose/<name>.json`        |
| Upstream styles, parity only   | `.upstream-registry/<base>-<style>/<name>.json`       | never published                            |
| Catalogs                       | `public/r/registry.json`, `index.json`, `config.json` |                                            |

Rewrites are in `next.config.mjs`; the retired blend-mode URLs redirect to the Fabricator one. Endpoints under `/r/**` return `application/json` with permissive CORS and long CDN caching.

## Done when

- [ ] A full `bun run registry:build` ran; the committed indexes changed with it and nothing gitignored is staged.
- [ ] Every placeholder has a rule in every style map it needs (the build's coverage lint).
- [ ] `shadcn add --dry-run` of a new or changed item succeeds against the local registry for each base.
