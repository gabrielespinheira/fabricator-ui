The panel under the calendar sets its `variant`, `size`, `businessHours`, `continuous`, `editable` and three of its `settings`, and the code beside it shows the props for what you pick, defaults left out. Pick a view in the calendar's own select (or press `d`, `4`, `w` or `m`) and the code adds `defaultView`; until then the calendar chooses the week, or three days when it's narrow. Scroll sideways with two fingers on a trackpad, or Shift and the wheel, and the days move under the hours a day at a time. Drag across empty time to create an event, drag an event to move it (hold Alt or Option to copy it), and drag its edge to change its length. Click an event for its details, right-click it for a menu, and press `?` for the keyboard shortcuts. Moving one Standup asks whether it changes that day, the days after, or the whole series. Every change can be undone from its toast or with ⌘Z.

Event Calendar is part of the Fabricator style. It draws [FullCalendar 7](https://fullcalendar.io/docs/react) with the library's own look: every element of the grid takes the style map's classes, and the events, panels, forms, menus and dialogs are the library's components. What a view shows, where a keyboard move lands, how a recurring edit splits a series and which months load are decided by a model with no FullCalendar or DOM in it, shared with React Native.

## Usage

```tsx
import {
  EventCalendar,
  type CalendarEvent,
} from "@/components/ui/event-calendar"
```

```tsx
const [events, setEvents] = React.useState<CalendarEvent[]>(initialEvents)

<EventCalendar
  events={events}
  onEventChange={(change) => setEvents(change.apply)}
/>
```

That is the whole calendar: the header (the title, which opens a date picker, Today, previous and next, the view, settings and Create), the week on a wide calendar and three days on a narrow one, creating, moving, resizing, editing and deleting, recurring edits, undo and the keyboard. Give it a height through `className` (it's 44rem until you do) or a parent with one.

An event is a plain object. `start` and `end` are ISO 8601 strings: a date alone for an all-day event, a time without an offset for wall time in the calendar's zone, or an offset or `Z` for an exact instant. `end` is exclusive, as in iCalendar.

```tsx
const event: CalendarEvent = {
  id: "planning",
  title: "Sprint planning",
  start: "2026-11-16T10:00:00",
  end: "2026-11-16T11:30:00",
  calendarId: "team",
  location: "Atlas, 3rd floor",
}
```

`defaultEvents` instead of `events` lets the calendar keep the list itself, which suits a prototype.

## Saving changes

`onEventChange` receives every change: created, duplicated, moved, resized, edited, deleted, undone and redone. The change says what the person did and which stored events to write:

```tsx
<EventCalendar
  events={events}
  onEventChange={async (change) => {
    // change.reason: "create" | "move" | "resize" | "edit" | "delete" | …
    // change.created, change.updated, change.deleted: what to store
    await saveEvents(change)
    setEvents(change.apply)
  }}
/>
```

The calendar shows the change at once. While the returned promise is pending the event is drawn as pending; if it rejects, the change reverts and a toast offers Retry. `change.apply` turns a list into the next one, so `setEvents(change.apply)` works as a state updater.

Without `onEventChange`, a controlled `events` list is read-only. Pass `editable={false}` to make any calendar read-only.

## Loading events

`load` replaces `events` for calendars backed by a server. It's called once per month, with the month's range and an `AbortSignal`, and the neighbouring months load ahead.

```tsx
<EventCalendar
  load={async ({ start, end, signal }) => {
    const response = await fetch(
      `/api/events?start=${start.toISOString()}&end=${end.toISOString()}`,
      { signal }
    )
    return response.json()
  }}
  onEventChange={(change) => saveEvents(change)}
/>
```

A month loads once and stays until the calendar holds 24, when the months farthest from the view are dropped; a month that leaves the view before it arrives is cancelled through the signal. A change patches the loaded months it touches, so an event moved across a month boundary shows in the new one at once. A sweep runs along the top edge while the visible months load, and a failed month shows Try again. `refetch()` on the controller loads every month again.

## Continuity

Day, N days and Week scroll sideways a day at a time: two fingers on a trackpad, Shift and the wheel, or a swipe on a touch screen. The columns follow the scroll and glide to the nearest day when it stops, so a view can start on any day, a week from Wednesday to Tuesday or four days from Saturday. From there the arrows move by the days in view, and Today or a date picked from the title lines the week up again. A long scroll keeps going: the calendar draws a page of days either side and moves on as it nears their edge.

```tsx
<EventCalendar events={events} continuous={false} />
```

`continuous={false}` steps a whole period at a time instead. With weekends hidden, the scroll moves over weekdays only. On React Native the engine pages by the period: a fling carries across days in Day, and across pages in Week and N days, before it snaps.

## Calendars

`calendars` are the sources an event belongs to through `calendarId`. Each has a colour and can be hidden or read-only.

```tsx
const calendars: CalendarSource[] = [
  { id: "work", name: "Work", color: "blue" },
  { id: "team", name: "Team", color: "green" },
  { id: "holidays", name: "Holidays", color: "orange", editable: false },
]
```

A colour is one of `red`, `orange`, `yellow`, `green`, `teal`, `cyan`, `blue`, `indigo`, `purple`, `pink` and `gray`, a colour role (`"info"`, `"success"`, …), or `{ hue, chroma }`. Each runs through the colour role recipe, so its text meets 4.5:1 in light and dark. An event's own `color` wins over its calendar's.

## Recurring events

`recurrence` holds RRULE and EXDATE lines, with `start` as the first occurrence:

```tsx
{
  id: "standup",
  title: "Standup",
  start: "2026-11-02T09:30:00",
  end: "2026-11-02T09:45:00",
  recurrence: "RRULE:FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR",
}
```

The model reads DAILY, WEEKLY, MONTHLY and YEARLY with INTERVAL, COUNT, UNTIL, BYDAY (with positions such as `3TU` and `-1FR`), BYMONTHDAY, BYMONTH and WKST, which covers every repeat Google Calendar offers. Occurrences are expanded in the calendar's zone, so 9:30 stays 9:30 across a daylight saving change.

Changing or deleting an occurrence asks for its scope. **This event** adds an EXDATE to the series and stores the occurrence on its own, with `recurringEventId` and `originalStart`. **This and following events** ends the series with UNTIL (or a shorter COUNT) and starts a new one. **All events** moves the series by the same day and time change. The change's `created`, `updated` and `deleted` hold exactly those writes.

## Time zones and locale

`timeZone` takes an IANA name and defaults to the device's zone. `locale` takes a BCP 47 tag and defaults to `"en-US"`, so the server and the browser agree; it sets the titles, the times, the 12 or 24 hour clock and the first day of the week, which the settings can change.

```tsx
<EventCalendar timeZone="Europe/Lisbon" locale="pt-PT" events={events} />
```

## Customising events

`renderEvent` replaces the chip. `EventCalendarEvent` is the default chip, to wrap or reuse:

```tsx
<EventCalendar
  events={events}
  renderEvent={(props) => (
    <EventCalendarEvent {...props} color="info">
      {props.event.title} · {props.timeText}
    </EventCalendarEvent>
  )}
/>
```

Keep the function stable (defined outside the component or memoized), since FullCalendar redraws events when it changes.

## Using FullCalendar directly

`fullCalendar` takes any [FullCalendar option](https://fullcalendar.io/docs) and merges it last. It's the way to add FullCalendar plugins, such as `@fullcalendar/icalendar`, or a view the calendar doesn't offer. It exists on the web only.

FullCalendar's Premium plugins (timelines, resource views, print) are not part of Event Calendar and need a licence of their own: AGPLv3 for open-source projects, commercial otherwise. With a licence, pass the plugins and your `schedulerLicenseKey` through `fullCalendar`.

```text
EventCalendar                    frame, variant, size, keyboard, toasts
├── EventCalendarHeader
│   ├── EventCalendarTitle       the period, and a date picker on press

    ├── EventCalendarEvent       each event's chip
    ├── EventCalendarEventDetails

```

`<EventCalendar>` with no children renders that layout; with children, it renders yours. For parts outside it, such as a sidebar, create the controller with `useEventCalendar` and pass it to each part as `calendar`:

```tsx
const calendar = useEventCalendar({ events, calendars, onEventChange })

<aside>
  <EventCalendarCreateButton calendar={calendar} />
  <EventCalendarMiniMonth calendar={calendar} />
  <EventCalendarSources calendar={calendar} />
</aside>
<EventCalendar calendar={calendar} />
```

## Accessibility

- Events are buttons named by their title and time; FullCalendar's grid passes axe and marks today with `aria-current="date"`.
- Dragging has a keyboard path (pick up with Space, move with the arrows) and a menu path (right-click, or Edit in the details), so nothing needs a pointer.
- Moves, creations, deletions and undos are announced in a polite live region.
- Details and forms move focus into themselves and return it when they close. The recurring scope question is a dialog with a radio group.
- Event colours meet 4.5:1 for text in light and dark; past events keep their text colour and only lighten their wash.

## Performance

The calendar is built for calendars far larger than a screen: the Large calendars example above holds about 100,000 events. What it does, and what to keep doing in your app:

- **Load by range.** With `load`, the calendar holds a few months, not your whole history: the months in view, the months either side ahead of time, and at most 24 kept. Requests for months that leave the view are cancelled through `signal`, so pass it to `fetch`. A list in `events` works into the tens of thousands; past that, or when the events live on a server, use `load`.
- **Indexed events.** Events are sorted once by start, so a new week or month finds its events by binary search instead of a pass over every event, and an edit re-indexes reusing every date already parsed. Dates parse once per object, so keep event objects immutable: `change.apply` returns a new list that reuses every unchanged event.
- **Only the range in view.** FullCalendar gets the visible range and the period either side, with recurring series expanded there. A time slot shows four events side by side and `+N` for the rest, a month cell shows what fits and "N more", and the agenda is virtualized by day. Past 60 events in a time grid, chips draw opaque instead of frosted, since every blurred chip is a compositing layer of its own.
- **React scheduling.** The grid's events are a deferred value, so the toolbar answers at once and the grid redraws in a render React can interrupt; changes run in transitions with `useOptimistic`, so an edit shows before the server answers. Chips are memoized and their date formats cached, so moving one event redraws one event.
- **Drag to create.** In Day, N days and Week the engine draws the event being dragged out itself, on one element that only moves while you drag, so a drag never adds or removes elements; FullCalendar's selection, which does on every move, handles the all-day row, month cells and touch.
- **Keep props stable.** Options and callbacks stay stable for the calendar's life; keep `events`, `calendars`, `renderEvent` and `fullCalendar` stable too (state, a module constant or `useMemo`), or every render re-reads them.
